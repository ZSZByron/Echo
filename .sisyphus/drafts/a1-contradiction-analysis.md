## 2. 最具讽刺性的铁证（M2 核心）

08-24 重构 commit `e046a3c` 的 diff 显示，重构者**触碰并改进了解析器**：

```diff
+            if "." in tag:  # strip optional dim prefix (e.g. LAW.world_structure)
+                tag = tag.split(".", 1)[1]
```

他们在 `_build_dimension_result_set` 里**添加了前缀剥离逻辑**（让它能兼容 `LAW.world_structure=...` 带维度前缀的格式）——说明重构者：
1. **知道解析器存在**
2. **知道它消费 tag=value 格式**
3. **甚至好心增强了它的容错性**

但**从未运行过一次端到端检查**："我新建的访谈器（输出简洁中文）还会产出这个格式吗？" 答案是永远不会。**改进消费方的同时斩断生产方，两处改动在同一个 commit 里。**

这不是"没人做"，是"两份各自正确的规范在同一个提交里互相拆台，且没有集成验收拦截"。

### M3：v0.1"机械投影"决策的前提已死（决策时信息缺失）

v0.1（08-27）立场："定稿时刻的数据只有结构化问答（module.subfield → value），实体识别与关系抽取尚未发生"——**这句话本身是诚实的**（当时 answers 确实只剩纯文本），但没人知道"尚未发生"其实是"三天前被移除"。决策程序正确，决策依据残缺。

> 考古回答用户之问："机械投影投的是什么？"——投的是 **key 层结构**（问卷骨架）。value 层的内容级结构化（编译器时代的 tag=value，及 v0.4 设想的槽位制）在决策日已不存在。**"结构化文件"在 08-21 的官方含义就是 answers 里的 tag=value 片段**（guide_engine 注释原话），该含义随 08-24 重构死亡；此后"结构化"一词漂移为三种含义（见 M8）。

### M4：08-28 实测症状未触发根因调查

明华实测 0 CROSS/0 cst 被如实记录（PROJECT_STATE），但调查止步于"两条填充路径都不产 tag= 片段"——**没有人问"这个格式是谁设计来产出的？那个机制去哪了？"** 一次 `git log -S "tag="` 就能还原的真相，晚了6天。

### M5：08-31 设计知情推迟，且定性错误

设计文档 §10 写"不做 **cst_\* 约束节点复活**（tag= 片段协议**另行立项**）"——"复活"一词暴露了定性：把它当成"从未实现过的功能"。实际上它是"曾完整工作后被废弃的功能"。定性错误导致修复方向错误：
- 按"从未实现"→ 需要新建协议（重量级，自然推迟）
- 按"曾被杀死"→ 只需恢复/重设计生产方（轻量级，可并入当次改造）

### M6：09-02 P0 诊断仍未回溯

"约束编译死路"被列为 P0 待修，机制描述完全正确，但历史归因依然缺席。若按 P0 的字面理解立项修复，会重新发明一个 08-21 已经存在过的东西。

### M7：理论演进与实现脱节（七层缺失的根源）

v0.1（08-27）实现立场：行政拓扑，模块扁平 L2。v0.4（08-28）理论权威：L0-L6 七层语义拓扑+槽位注册表+物化协议。**理论文档在其后持续演进（v0.1→v0.4），实现从未跟进**——因为实现的直接上游（结构化层）已死，七层无从谈起。七层缺失不是独立缺口，是 M1 的下游症状。

### M8："结构化"一词的三义漂移（沟通病根）

| 时期 | "结构化文件"的含义 | 载体 |
|------|------------------|------|
| 08-21 实现层 | answers 里存 `tag=value;` 机器标记的字典 | guide_engine 注释"structured file (answers)" |
| 08-28+ 设计层 | v0.4 槽位注册表：填空类型+词典概念+拓扑产出+派生策略 | 治理文档 |

三层各说各话。用户的"我一开始要求的就是结构化文件"指第2种；08-21 实现的是第1种；现行代码是第3种。**没有任何一次会议/文档把三者对齐。**

## 5. 病根定性

**不是任何单点失误，是三个机制缺失叠加：**

1. **契约无注册表**：生产方/消费方的格式约定散落在两份代码注释里，没有一份双方签字的 schema 文档（tag_dictionary.yaml 算半个，但 08-24 后无人核对它的消费方还活着）
2. **集成验收缺位**：单测各自 mock 输入全部通过；没有任何测试断言"访谈器产出 → 解析器消费"贯通（一条集成测试即可拦截 M1/M2）
3. **观测-归因断层**：08-28、08-31、09-02 三次观测到症状，三次都止于现象描述，无一次做历史回溯（git log -S 三秒钟可得答案）

## 6. 与架构文档的对接（修复方向）

本次考古**修正**架构文档（`a1-knowledge-graph-architecture.md`）的两处定性：

1. §2.2 "约束编译死路（设计存在但恒0）" → 修正为："**曾是完整闭环（08-21），被 08-24 范式重构斩断，消费方遗留至今**"。决策5的三个方案因此重新估值：方案2（定稿时 LLM 统一结构化）不是"新发明"，是**用新范式（LLM）重建生产方**——正是 08-24 本该做的事。
2. 新增第 0 号开放问题（用户建议采纳）：**"结构化文件的权威契约"必须先于任何实现定案**——v0.4 槽位注册表（内容级）+ 本次架构的 §3.3 LLM 产出 JSON 契约（条目级）共同构成，生产方（统一 LLM 调用）与消费方（投影/约束编译/深度树挂载）双方签字后才动工。

**流程铁律沉淀（从本次事故学习）**：
- 凡生产方/消费方格式对，必须有共同签字的 schema 文档 + 一条端到端集成测试（CI 拦截断链）
- 凡"X 未实现"的诊断，必须先跑 `git log -S "X"` 排除"曾实现后被废"
- 凡范式重构，必须盘点被替换组件的全部下游消费方（deprecation checklist）
