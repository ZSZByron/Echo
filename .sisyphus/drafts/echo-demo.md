# Draft: 回声·AI交互式规则终端 Demo

## Requirements (confirmed)
- 项目名：回声 (Echo)
- 核心架构：三明治模型（表现层 / 认知层 / 逻辑层）
- 工作目录：H:\UGC（空目录，从零开始）
- 这是 Demo 项目（面试/演示用途）

## 架构蓝图（来自用户）
- **模块 A - 交互终端**（前端）：React + Tailwind，输入框 + 状态区 + 流式打字机渲染
- **模块 B - 意图解析器**（后端AI）：LLM + Prompt，自然语言 → 结构化JSON指令
- **模块 C - 核心规则引擎**（后端Python）：FastAPI + Python逻辑，冷酷判决
- **模块 D - 叙事渲染器**（后端AI）：LLM + Prompt，JSON结果 → 赛博朋克流式文本
- **模块 E - 世界数据库**：SQLite/JSON，存储神王表/世界规则/玩家状态

## 核心交互循环
玩家输入 → 意图解析 → 规则判定 → 叙事渲染 → 流式输出（3-5秒内）

## Technical Decisions (CONFIRMED)
- **前端**：Vite + React + TypeScript + Tailwind CSS
- **后端**：FastAPI + Python
- **AI Provider（Q1=C 升级版）**：全量兼容 — 统一LLM Provider抽象层，支持 OpenAI/Anthropic/通义千问/Kimi/GLM/DeepSeek 等所有OpenAI兼容API。配置=base_url+api_key+model即可切换。
- **数据存储（Q2=C）**：混合方案 — 静态世界设定（神王表/世界规则/场景）用JSON/YAML，玩家运行时状态用SQLite
- **流式通信（Q3=C）**：后端一次性返回完整文本，前端JS逐字模拟打字机效果。简化实现
- **Demo内容（Q4=A）**：单一场景深Demo — 神殿废墟，3-5条核心神王规则，完整成功/失败/神王干涉分支
- **前端框架（Q6=A）**：Vite + React + TypeScript

## Test Strategy (Q5 - 多层防御，极其严格)
用户要求五层测试关卡：
1. **单元测试** (pytest) — 规则引擎核心判决逻辑
2. **Gherkin/BDD测试** (pytest-behave) — 业务场景验证
3. **QA场景测试** — 端到端验收
4. **覆盖率** (pytest-cov) — 强制达标
5. **代码质量指标** (ruff/mypy) — 静态分析
6. **变异测试** (mutmut) — 故意塞错验证测试质量

每个任务都要经历这些关卡，一关接一关。

## 四 Agent 流水线（用户新增需求 - 核心质量门禁）

用户要求在计划中嵌入一条四阶段 Agent 流水线，每个阶段由专门 Agent 负责：

### Stage 1: 需求规格化 Agent
- 职责：将任务描述转化为精确的、可验证的规格说明
- 输出：结构化的需求文档（输入/输出/边界/验收标准）
- 门禁：规格必须无歧义、可测试

### Stage 2: 编码 Agent
- 职责：基于规格实现代码 + 单元测试
- 输出：可运行的代码 + 通过的测试
- 门禁：单元测试全通过

### Stage 3: 重构 Agent
- 职责：优化代码结构，消除技术债
- 关注点：DRY/SOLID/可读性
- 门禁：测试仍全通过 + 质量指标达标

### Stage 4: 架构审查 Agent
- 职责：最终架构合规性判定
- 用户监控指标：
  - **测试覆盖率** (coverage %)
  - **依赖结构** (模块间耦合，无循环依赖)
  - **圈复杂度** (cyclomatic complexity，单函数 ≤ 10)
  - **模块大小** (单文件行数上限)
- 门禁：所有指标达标才允许标记任务完成 → 可交付

### 流水线运行方式
- 每个实现任务都经过这4个阶段
- 阶段间有明确的"通过/打回"机制
- 用户通过量化指标判定，不靠主观感觉
